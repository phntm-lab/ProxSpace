Среда разработки Proxmark3 для Windows — одним исполняемым файлом.

Положите `proxspace.exe` в пустую папку и запустите. Он скачает msys2,
распакует его рядом с собой, настроит, установит тулчейн, нужный для сборки и
запуска [Proxmark3](https://github.com/RfidResearchGroup/proxmark3), и откроет
шелл. Всё, что он создаёт, лежит в этой одной папке. Он готовит окружение и
только его: он не оборачивает клиент proxmark3, не управляет прошивками и не
общается с устройством.

## Релизы

Каждый релиз — это один файл, `proxspace.exe`, на
[странице релизов](https://github.com/phntm-lab/ProxSpace/releases/latest).
Больше ничего скачивать и устанавливать не нужно.

`proxspace update` спрашивает у GitHub, не вышла ли версия новее, и сообщает об
этом со ссылкой; сам себя бинарник никогда не заменяет, а неудавшаяся проверка
никогда не мешает тому обновлению, частью которого она была.

## Требования

|      |                                                                                |
| ---- | ------------------------------------------------------------------------------ |
| ОС   | 64-битная Windows                                                              |
| Диск | ~10 ГБ свободно, рекомендуется 15 ГБ                                           |
| Сеть | ~1 ГБ на первом запуске                                                        |
| Путь | только `A-Z a-z 0-9 . _ - \ /` и буква диска — без пробелов, скобок и не-ASCII |

Правило пути соблюдается принудительно: ниже по цепочке этот путь никто не
экранирует, поэтому `proxspace` отказывается стартовать, а не падает позже так,
что причину не найти.

## Быстрый старт

1. Создайте папку, путь к которой подходит под правило выше: `C:\ProxSpace` или
   `D:\dev\proxspace` подойдут, `C:\My Projects\ProxSpace` — нет.
2. Положите в неё `proxspace.exe` и запустите. Первый запуск не быстрый; Ctrl+C
   его останавливает, повторный запуск продолжает с места остановки.
3. В открывшемся шелле соберите прошивку:

   ```
   git clone https://github.com/RfidResearchGroup/proxmark3.git
   cd proxmark3
   make clean && make -j
   ```

4. Клиент запускается командой `pm3`, прошивка — `pm3-flash-all`. Это
   собственные скрипты Proxmark3; ProxSpace лишь даёт окружение, в котором они
   работают.

## Команды

| Команда                            | Что делает                                           |
| ---------------------------------- | ---------------------------------------------------- |
| `proxspace`                        | Готовит окружение, если нужно, и открывает шелл      |
| `proxspace shell [-- args]`        | То же самое, аргументы передаются login-шеллу        |
| `proxspace install [--force]`      | Устанавливает набор пакетов ProxSpace                |
| `proxspace update [флаги]`         | Обновляет окружение                                  |
| `proxspace repair [--rebase]`      | Переустанавливает пакеты поверх сломанного дерева    |
| `proxspace info`                   | Показывает версии, пути и состояние тулчейна         |
| `proxspace mirrors rank\|restore`  | Переупорядочивает или восстанавливает зеркала pacman |
| `proxspace exec -- <cmd>`          | Выполняет одну команду внутри окружения              |
| `proxspace autobuild`              | Собирает каждый чекаут Proxmark3 в `pm3/`            |
| `proxspace clean [--cache\|--all]` | Освобождает место или удаляет окружение              |

Глобальные флаги — их можно ставить и до, и после подкоманды:

| Флаг              | Что делает                                                     |
| ----------------- | -------------------------------------------------------------- |
| `-y`, `--yes`     | Отвечает «да» на каждый вопрос, для запусков без человека      |
| `-q`, `--quiet`   | Печатает только предупреждения, ошибки и вывод команд          |
| `-v`, `--verbose` | Печатает подробности, которые обычно уходят только в лог       |
| `--no-color`      | Никогда не раскрашивает вывод                                  |
| `--dir <path>`    | Работает с другой папкой, не с той, где лежит исполняемый файл |

### shell

Открывает login-шелл в `pm3/` — внутри это одновременно `$HOME` и `/pm3`.
Окружение сначала поднимается, если чего-то не хватает, так что отдельного шага
установки помнить не нужно. Неинтерактивная форма — `proxspace shell -- -c
"make -j"`, её код возврата передаётся наружу.

### install

Ставит набор пакетов, который несёт эта сборка. Обычно её вызывает сам `shell`;
`--force` переустанавливает каждый пакет поверх себя — это то, что нужно
перенесённой папке или недоделанной установке.

### update

По умолчанию выполняются обе половины.

| Флаг                | Что делает                                                                                                            |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `--msys2`           | Только базовая система msys2 (`pacman -Syuu`, либо полная переустановка дерева, которое уже нельзя обновить на месте) |
| `--packages`        | Только набор пакетов ProxSpace                                                                                        |
| `--check`           | Говорит, что сделала бы каждая половина, и ничего не меняет                                                           |
| `--reinstall-msys2` | Заменяет дерево, даже если его можно было обновить                                                                    |
| `--no-reinstall`    | Вместо замены только сообщает, какой бы ни была версия                                                                |

### repair

Переустанавливает каждый установленный пакет поверх себя. Это для дерева, у
которого файлы испорчены так, что снаружи не разобраться: недописанный пакет,
неинициализированная связка ключей, повреждённые базы.

`--rebase` дополнительно пересчитывает адреса загрузки DLL msys2 (`rebaseall`).
Это долго, требует закрыть все процессы ProxSpace и лечит ровно один симптом:
сборки, случайно падающие с `unable to remap`.

### info

Печатает версии, пути, состояние msys2 и пакетов, найденный тулчейн и немного о
машине, а тот же текст пишет в `proxspace-info.txt`, чтобы его можно было
приложить к отчёту об ошибке. Единственная команда, которая работает на
сломанной или отсутствующей установке.

### mirrors

`mirrors rank` замеряет каждое зеркало pacman и переупорядочивает списки от
быстрых к медленным, сохраняя исходный порядок в резервной копии. `mirrors
restore` возвращает порядок, с которым пришёл msys2. Стоит попробовать, если
загрузки еле ползут или отваливаются по таймауту.

### exec

`proxspace exec -- gcc --version` выполняет одну команду в окружении и
возвращает её код выхода. Каждое слово передаётся как есть; если нужен
синтаксис шелла — `exec -- bash -c "..."`.

### autobuild

Собирает каждый чекаут Proxmark3 в `pm3/` и пакует каждый в
`builds/<name>/<name>-<date>-<hash>.7z`. Каждый чекаут он сначала подтягивает
(`git pull --ff-only`) и пропускает, если архив на этот коммит уже есть; иначе
собирает и складывает клиент, прошивку, recovery-образы, драйвер Windows и
нужные клиенту DLL — так, чтобы архив запускался на машине без ProxSpace.

`p7zip` доставляется при первом запуске, если его нет, а `builds/` монтируется
как `/builds` только на время работы команды.

### clean

`--cache` (по умолчанию) очищает кэш загруженных пакетов pacman — это гигабайты
ценой более долгой переустановки. `--all` удаляет дерево msys2 целиком. Ни то,
ни другое не трогает `pm3/` и `builds/`: всё, что они удаляют, можно скачать
заново, и ничего вашего там нет.

## Что появляется на диске

Всё лежит рядом с исполняемым файлом — ничего не пишется ни в `%APPDATA%`, ни в
`%TEMP%`, ни в профиль пользователя, поэтому папку можно перенести или
скопировать целиком:

```
<папка>/
├── proxspace.exe
├── msys2/                  дерево msys2
├── pm3/                    ваш домашний каталог внутри шелла; исходники Proxmark3
├── builds/                 результат `proxspace autobuild`
├── proxspace.state.json    что уже установлено
├── proxspace-info.txt      последний отчёт `proxspace info`
└── proxspace.log           что происходило, включая вывод внешних команд
```

Перенос и переименование папки поддерживаются. Следующий запуск это заметит,
скажет об этом и предложит переустановить пакеты: пакеты помнят путь, под
которым были установлены, и перенесённому окружению переустановка нужна прежде,
чем оно снова начнёт собирать.

## Внутри шелла

`MSYSTEM` — `UCRT64`, `$HOME` — `/pm3`, а `/opt/proxspace/bin` стоит в `$PATH`.
В этом каталоге лежат:

| Имя                                                                                     | Что это                                                                                                         |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `pm3`, `pm3-flash`, `pm3-flash-all`, `pm3-flash-bootrom`, `pm3-flash-fullimage`         | Обёртки, запускающие одноимённый скрипт из того чекаута, в котором вы стоите, — поэтому `pm3` работает без `./` |
| `proxspace`                                                                             | Тот самый исполняемый файл снаружи, доступный по имени изнутри                                                  |
| `ps-setup`, `ps-info`, `ps-repair`, `ps-upgrade`, `ps-rankmirrors`, `ps-restoremirrors` | Имена из оригинального ProxSpace, теперь каждое — однострочный шим к своей подкоманде                           |

## Что устанавливается

msys2 `20260611`, скачанный с `mirror.msys2.org` и сверенный с sha256, зашитым в
исполняемый файл, плюс набор пакетов из `assets/packages.txt`: `git`, `make`,
`pkgconf`, `base-devel`, `procps-ng`, тулчейн UCRT64 (`gcc`, `gdb`, `cmake`),
кросс-тулчейн ARM (`arm-none-eabi-gcc`, `newlib`, `gdb-multiarch` и
зафиксированный `binutils`), `qt6-base`, `readline`, `libsndfile`, `lua`,
`bzip2`, `jansson`, `openssl`, `lz4`, `libgd`, `opencl-icd`, `openocd` и Python
с `pip`, `setuptools` и `cryptography`. Пакеты ChameleonMini/AVR из оригинала
поставляются закомментированными.

Список пишется в дерево как `/opt/proxspace/packages.txt`, так что установленное
можно прочитать из самого окружения.

## Коды возврата

| Код   | Значение                                                |
| ----- | ------------------------------------------------------- |
| `0`   | Сделал то, что просили                                  |
| `1`   | Не смог, и сказал почему — в stderr и в `proxspace.log` |
| `2`   | Ошибка в командной строке                               |
| `130` | Остановлено по Ctrl+C                                   |

`shell`, `exec` и `autobuild` вместо этого возвращают код той программы, которую
запустили.

## Если что-то пошло не так

| Симптом                                                                          | Что делать                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Отказывается стартовать и называет символ в пути                                 | Перенесите папку туда, где нет пробелов, скобок и не-ASCII                                                                                                                                                          |
| Загрузки еле ползут, отваливаются по таймауту или pacman не достучится до зеркал | `proxspace mirrors rank`, затем упавшая команда; `mirrors restore` вернёт исходный порядок                                                                                                                          |
| Не проверяется подпись пакета или повреждены базы                                | `proxspace repair` — переустановит всё поверх себя и обновит связку ключей и базы                                                                                                                                   |
| Сборки случайно падают с `unable to remap` или ошибкой `fork`                    | Закройте все окна ProxSpace и запустите `proxspace repair --rebase`. Это коллизия базовых адресов DLL cygwin; оригинал ради этого гонял `rebaseall` на каждом старте                                                |
| pacman говорит, что база заблокирована                                           | Работает другой pacman — закройте прочие окна ProxSpace. Блокировку, оставшуюся от убитого pacman, ProxSpace снимает сам                                                                                            |
| «Файл занят» при удалении или замене                                             | В сообщении назван держащий его процесс: открытый шелл, редактор, сборка, `gpg-agent` или антивирус, сканирующий дерево. Закройте его и повторите команду                                                           |
| Установка или обновление прервались                                              | Запустите ту же команду ещё раз. Каждый завершённый шаг записан в `proxspace.state.json`, поэтому работа продолжится, а не начнётся заново                                                                          |
| `update --check` полминуты молчит                                                | Он спрашивает у GitHub, не вышел ли ProxSpace новее. Без сети это ожидание — таймаут TLS-рукопожатия; остальная часть команды работает как обычно                                                                   |
| Что-то другое                                                                    | `proxspace info` записывает в `proxspace-info.txt`, чем окружение оказалось на самом деле, а в `proxspace.log` лежат все сообщения и полный вывод всех внешних команд. Оба файла стоит приложить к отчёту об ошибке |

`proxspace.log` копится от запуска к запуску; перевалив за 5 МБ, он
отодвигается в `proxspace.log.old`, и запись начинается заново.

## Чем отличается от оригинального ProxSpace

Это переписанный [Gator96100/ProxSpace](https://github.com/Gator96100/ProxSpace),
который держал msys2 внутри репозитория и управлял им из `.bat` и shell-скриптов.
Поведение отличается сознательно:

|                                               |                                                                                                                                                                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Один исполняемый файл                         | Вместо `runme64.bat`, `autobuild.bat`, `setup.cmd` и `setup/bin/*`; старые имена по-прежнему живут шимами внутри шелла                                                                                          |
| msys2 скачивается, а не лежит в репозитории   | Репозиторий остаётся маленьким, а базовая система проверяется по контрольной сумме на входе                                                                                                                     |
| UCRT64 вместо MINGW64                         | `MSYSTEM=UCRT64`, `PYTHONHOME=/ucrt64` и пакеты `mingw-w64-ucrt-x86_64-*`                                                                                                                                       |
| Установка — явный возобновляемый конвейер     | Оригинал полагался на двойной запуск шелла, потому что `pacman -Syuu` не может продолжаться в процессе, чей msys2-рантайм он только что заменил. Теперь каждый завершённый шаг записан в `proxspace.state.json` |
| Изнутри login-шелла ничего не устанавливается | Оригинальный `09-proxspace_setup.post` гонял pacman прямо при входе; здесь хук только настраивает окружение                                                                                                     |
| Есть лог                                      | Всё напечатанное плюс полный вывод каждой внешней команды дублируется в `proxspace.log`                                                                                                                         |
| `rebaseall` не гоняется на каждом старте      | Он доступен как `proxspace repair --rebase`                                                                                                                                                                     |
| Есть путь назад                               | `proxspace clean` освобождает кэш или удаляет окружение, не трогая `pm3/` и `builds/`                                                                                                                           |

## Разработка

Всё, что ниже, — для того, кто меняет сам ProxSpace. Как присылать правку —
проверки, стиль коммитов, что должен нести pull request — написано в
[CONTRIBUTING.md](.github/CONTRIBUTING.md).

### Сборка и проверки

| Команда                                     | Зачем                                                                               |
| ------------------------------------------- | ----------------------------------------------------------------------------------- |
| `cargo build --release`                     | Тот самый бинарник: thin LTO, один codegen unit, символы вырезаны                   |
| `cargo test`                                | Всё и за секунды — ничего здесь не ходит в сеть и не трогает настоящее дерево msys2 |
| `cargo test -- --ignored`                   | Три теста, которые как раз ходят: настоящий базовый архив и настоящее зеркало       |
| `cargo fmt --check`                         | Форматирование, ровно как его гоняет CI                                             |
| `cargo clippy --all-targets -- -D warnings` | Линты; предупреждения здесь и в CI — ошибки                                         |

Нижняя планка тулчейна — `rust-version` в `Cargo.toml` (1.85, edition 2024).

`--dir <path>` заставляет любую команду работать с другой папкой, а не с той,
где лежит исполняемый файл: так debug-сборку направляют на временное дерево
вместо того, что лежит рядом с `target/debug/`.

### Карта модулей

Логика живёт в `src/lib.rs`, а не в `main.rs`, чтобы интеграционные тесты могли
дёргать её напрямую, а не только через командную строку.

Модули разложены по слоям, и слой может называть только себя или слой,
лежащий глубже:

| Слой    | Модули                                                                                                                  | Чем владеет                                                                                                                                                                                                                   |
| ------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `core`  | `paths`, `state`, `packages`, `plan`, `update`, `versions`, `preflight`, `pacman`, `assets`, `fstab`, `userdb`, `msys2` | Данные и решения: где что лежит, что означает файл состояния, какие пакеты и какой msys2 ставит эта сборка, что делать с деревом при обновлении, как должен выглядеть `pacman.conf`. Достижимо без диска, сети и подпроцессов |
| `ui`    | `ui`, `logging`, `interrupt`                                                                                            | Все сообщения пользователю, лог, куда они дублируются, Ctrl+C                                                                                                                                                                 |
| `ports` | `command`, `http`                                                                                                       | Два выхода из процесса, у которых есть вторая реализация в тестах: запуск другой программы и сеть                                                                                                                             |
| `infra` | `process`, `http`, `download`, `archive`, `assets`, `paths`, `preflight`, `state`, `pacman`, `msys2`                    | Всё, что действительно трогает диск, сеть или другую программу: запуск, закачка и распаковка, запись ассетов, файлов учётной записи и `pacman.conf`, чтение файла состояния обратно                                           |
| `app`   | `install`, `repair`, `provision`, `update`, `clean`, `autobuild`, `info`, `mirrors`, `release`                          | Что делает каждая команда, стадия за стадией                                                                                                                                                                                  |
| `cli`   | `args`, `dispatch`                                                                                                      | Дерево команд, которое разбирает clap, и единственный `match`, через который проходит каждая команда                                                                                                                          |

Несколько имён встречаются дважды — `assets`, `paths`, `preflight`, `state`,
`pacman`, `msys2`, `http`. Это не дубли, а сам разрез: в `core` модуль говорит,
каким должен быть ответ, в `infra` — читает или пишет файл, который его несёт.
`core::pacman` решает, как должен выглядеть `pacman.conf` с нашим пином;
`infra::pacman::conf` этот файл пишет.

`core` и `ui` — равные на самом глубоком ярусе, и ни один не может назвать
другой: решения не должны знать, как их показывают, а экран не должен знать,
что решается. Всё это сторожит `tests/layers.rs`: он читает `src/` и считает
нарушением `crate::`-путь в чужой ярус — в `use`, в inline-пути и в doc-ссылке
одинаково.

Форму держат ещё два правила: внешние программы запускаются только через
`ports::command::CommandRunner`, в сеть ходят только через
`ports::http::HttpClient`. И то, и другое — трейты с подделками в тестах,
поэтому набор тестов работает офлайн. У всего остального, что выходит за
пределы процесса, второй реализации нет и трейта тоже.

Установка — лестница стадий, записываемая в файл состояния: `NotInstalled →
Downloaded → Extracted → Bootstrapped → CoreUpdated → PackagesInstalled →
Ready`. Каждый шаг идемпотентен и продолжается с последнего завершённого; новый
шаг — это новый вариант `Stage` и его место в этом порядке.

### Тесты

Юнит-тесты лежат в `src/*`, интеграционные — в `tests/`, по файлу на шов:
`install_flow` (весь конвейер на подделках), `cli`, `state`, `archive`,
`update_matrix` (каждая пара «установленная версия × сборка» и что она решает),
`download`, `provision`, `prepare`, `resources`, `docs` (таблицы команд обоих
README против дерева clap), `release_tag` и `layers` (правило зависимостей
выше). Фикстуры — настоящий `pacman.conf`, образцы `fstab` — в
`tests/fixtures/`.

Тесты названы предложениями о поведении, а не по имени проверяемой функции, и
каждый формулирует решение, которое принимает код. Пожалуйста, так и оставьте.

### Ресурсы Windows, `build.rs` и `rc.exe`

`build.rs` встраивает иконку, ресурс версии и манифест через `winresource`.
`FileVersion` и `ProductVersion` берутся из `CARGO_PKG_VERSION`, остальное
задано в самом скрипте. Он работает только для Windows-целей.

Для этого нужен компилятор ресурсов — `rc.exe` из Windows SDK или `windres` из
mingw-тулчейна. Машина, где нет ни того, ни другого, всё равно соберёт рабочий
`proxspace.exe`: неудача превращается в `cargo:warning`, а бинарник выходит
голым, потому что валить сборку из-за иконки — неверный размен.

Цена этому — то, что битая иконка или опечатка в манифесте тоже видны только
как это предупреждение. `tests/resources.rs` читает оба файла так же, как их
прочитает компилятор ресурсов — каталог иконки, заявленные в нём размеры,
манифест как XML, — чтобы ошибка в них роняла тесты, а не уезжала молча.

### Ассеты и как они попадают в дерево msys2

Оригинал держал их рядом с исполняемым файлом в `setup/` и монтировал этот
каталог как `/setup`. Здесь они лежат в `assets/`, вкомпилированы в бинарник
через `include_str!` и записываются в дерево функцией `infra::assets::install()`.
Поэтому рядом с бинарником никогда не появляется ничего, кроме `msys2/`, `pm3/`
и служебных файлов, а ассеты не могут разойтись по версии с кодом, который на
них рассчитывает.

| Источник                             | Куда ложится                               | Что это                                                                                                                                     |
| ------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `assets/09-proxspace_setup.post`     | `etc/post-install/09-proxspace_setup.post` | Подключается в конце каждого входа: `$PATH`, `MSYSTEM`, `PSVERSION`                                                                         |
| `assets/nsswitch.conf`               | `etc/nsswitch.conf`                        | Заставляет cygwin читать пользователей только из `/etc/passwd`, никогда из Windows                                                          |
| `assets/bin/pm3-wrapper`             | `opt/proxspace/bin/pm3*`                   | Один скрипт под пятью именами; разбирается по `basename $0`                                                                                 |
| `assets/bin/ps-shim`                 | `opt/proxspace/bin/ps-*`, `proxspace`      | Один шаблон на каждую подкоманду из `setup/bin` оригинала                                                                                   |
| `assets/packages.txt`                | `opt/proxspace/packages.txt`               | Набор пакетов дословно, чтобы его можно было прочитать из дерева                                                                            |
| `assets/autobuild.sh`                | `opt/proxspace/autobuild.sh`               | Скрипт сборки, которому передаёт управление `autobuild`                                                                                     |
| `assets/autobuild/{official,rrg}/**` | `opt/proxspace/autobuild/**`               | `.bat`-файлы, копируемые в каждый релизный архив; единственные ассеты с CRLF и единственные, которые этот бинарник никогда не запускает сам |

Три из них — шаблоны: `@PSVERSION@` в хуке и `@COMMAND@` в шиме подставляются из
констант времени компиляции и фиксированной таблицы в `assets.rs`. Ничто из
подставляемого не зависит от того, куда установлена папка, — именно это и
позволяет скопировать установленное дерево на другую машину.

Добавить ассет — значит добавить файл, `include_str!` и строку в
`assets::assets()`; `install()` пишет всё перечисленное там, приводит переводы
строк и помечает скрипты исполняемыми.

### Как поднять версию msys2

Все версионно-зависимые константы собраны в один блок в начале
`src/core/msys2.rs`, и подъём msys2 — это правка этого блока как целого:

1. Возьмите самый свежий `msys2-base-x86_64-<datestamp>.tar.xz` с
   <https://repo.msys2.org/distrib/x86_64/> и положите его датировку в
   `MSYS2_VERSION`.
2. Направьте `MSYS2_URL` на этот файл — имя архива разбирается обратно из URL,
   поэтому оно должно остаться апстримовым.
3. Скачайте его, посчитайте хеш, сверьте со вторым зеркалом и положите в
   `MSYS2_SHA256`. Апстрим не публикует файл с контрольной суммой, так что эта
   константа — единственное, что стоит между подменённой закачкой и установкой.
4. `MSYS2_MIN_COMPATIBLE` не трогайте, пока апстрим не сломает путь обновления
   со старых рантаймов. Поднять её — значит отправить всех, кто ниже этой
   версии, на полную переустановку вместо `pacman -Syuu`.

Версии сравниваются как строки, и это работает, только пока держится форма
датировки; тесты в том же модуле сверяют константы друг с другом и с этой
формой, а `tests/update_matrix.rs` покрывает, что решает каждая пара
«установленная версия × сборка».

### Как менять набор пакетов

Источник истины — `assets/packages.txt`: по пакету на строку, комментарии `#` и
`;` и — для зафиксированного `arm-none-eabi-binutils` — полный URL на
`.pkg.tar.zst`. Форма с URL существует потому, что репозиторная версия этого
пакета ломает сборку proxmark3; имя и версия выковыриваются из имени файла в
URL, поэтому оно обязано сохранять принятую в pacman форму
`name-version-release-arch`. Всё это проверяет `packages.rs` и отвергает
опечатку при разборе, а не посреди установки.

Перевести пин на другую версию — это правка одной строки; `pacman.rs` держит
блок `IgnorePkg` в `pacman.conf` в согласии с тем, что закреплено, так что
обновление не подменит пакет молча.

Изменение списка не требует никаких других правок — он и в дерево уезжает, и
разбирается из одной и той же строки.

### Соглашения

Обоснования живут в шапках модулей. Каждый `src/*.rs` начинается с блока `//!`,
где сказано, для чего модуль, что на его месте делал оригинальный ProxSpace и
почему то, что выглядит произвольным, устроено именно так: пин, класс символов в
`preflight`, лестница стадий, `-Scc` вместо `-Sc`. Прежде чем менять что-то
выглядящее бессмысленным, прочитайте шапку над ним; добавляя своё, оставьте
такую же заметку.

Комментарии — на английском, на каком бы языке ни шло обсуждение, из которого
они родились, и объясняют техническую причину, а не историю. `cargo doc
--no-deps --document-private-items` соберёт всё это, если так читать удобнее,
чем исходники.

Тесты называются предложениями о поведении, а изменение поведения без теста,
который до него падает, не закончено. Новая зависимость требует обоснования в
самом pull request: дерево зависимостей намеренно маленькое, и каждый крейт в
нём либо делает то, что за вечер не напишешь, либо и так приходит транзитивно.
